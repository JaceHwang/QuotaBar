# QuotaBar 内测体验与更新渠道设计

状态：用户已于 2026-11-05 确认按本设计实现；本文不代表功能已实现或版本已发布。

## 目标和已确认的选择

- macOS、Windows 均提供内测体验开关：默认关闭，用户必须经过多次手动确认才能开启；关闭时不提供内测更新。
- 用户选择 [B 独立卡片](2026-11-05-beta-experience-visual.md)，沿用现有设置风格并提示风险。
- 用户同意在公开 GitHub 仓库使用公开预发布：任何有仓库读取权限的人都可以下载，开关仅控制应用内更新资格，不是访问控制或邀请制。
- 用户选择一个 Pages 更新清单，正式版与内测版使用独立字段；两平台独立选择有效版本。安装继续由用户明确发起。
- 本设计不授权实际发布内测或正式版本，不涉及私有仓库、账号白名单、产品遥测或上传用户数据。

## 现状与约束

当前 `updates.json` 为 schema 1，仅含 `stable` 平台字段；Swift、C# 的版本解析、GitHub Release 校验和升级事务只接受三段数字，且排除 prerelease。仓库已有 beta 的 Release Please 配置，但 staged 打包适配器只接受正式标签；Beta 配置还需核实并补齐版本文件同步。当前 macOS 将 `CFBundleShortVersionString` 当作完整版本，Windows 从程序集数值版本取当前版本；这两者都不足以区分相同数字版本的多个 Beta。

保留 GitHub 发布资产的来源、摘要、平台和安装事务检查，保留此前验证过的取消、失败回滚以及用户数据保存行为。正式版本仍由 Release Please 管理，不覆盖任何已发布资产。项目已有未提交的统一消息列表修改，本设计不覆盖或包含其实现。

## 交互与状态

1. 「关于应用」的「版本与更新」下方显示独立的「内测体验」卡片，说明“可提前收到内测更新，版本可能不稳定；安装需手动确认”。状态清楚显示“已关闭”或“已开启”，默认灰色关闭。遵循已选视觉简报，三个语言、浅色/深色、高对比、键盘和读屏可用。
2. 用户触发开启时，开关保持关闭，先显示第 1 步风险说明，只有主动点击“继续”进入第 2 步；关闭窗口、Escape、取消或中断均不改变持久状态。
3. 第 2 步再次说明将接收内测更新，显示“取消”和“确认开启”；只有显式点击后、持久保存成功，开关才显示开启。默认焦点和回车行为不能使一次按键越过两步。存储失败时提示错误，继续保持关闭，不得使用内测资格。
4. 开启后，沿用既有自动检查和提醒开关：自动检查仍受用户设置控制；开启内测本身不自动下载安装。手动检查也按当前资格筛选。更新可用时清楚标明“内测版”或“正式版”，保留更新内容、稍后、跳过和用户点击“立即更新”。消息通知也带对应标识，历史消息不重放。
5. 用户可随时关闭内测；保存成功后立即只提供正式更新，废弃已发现或正在检查的内测结果及其待发提醒，不删除历史消息。对于正在下载、校验、准备且尚可取消的内测更新，先安全取消并清理，竞态按下文处理；进入不可撤销交接或安装阶段时暂时禁用开关，结束后恢复操作并说明原因。
6. 若用户已安装内测版后关闭开关，应用显示“当前运行内测版；关闭后不再接收内测更新，待有更新的正式版时可升级”。不自动降级或静默重装旧版；直到有语义版本更高的正式包才提示。关闭开关不会自动恢复之前版本。

设置仅保存在当前设备的现有用户数据目录内，使用独立的、有 schema 的更新渠道偏好文件；严格校验布尔类型，采用原子替换与可观察的写入结果。不能依赖 macOS `UserDefaults.set` 的无错误返回作为保存成功证明。内测偏好损坏时隔离原文件供诊断并按关闭处理，不得把其余设置重置或用默认值覆盖原设置；不存在、格式错误、未知 schema 或损坏均视为关闭，不能从旧备份静默恢复为开启。重启后保留用户成功保存的选择。关闭的写入若失败，开关保持显示已开启并明确告知“未保存，重启后仍会开启”，不能假装已持久关闭；当前会话暂停提供内测更新并允许重试。升级安装保留该文件，两平台均需验证写入成功和失败路径。

## 更新选择与版本身份

- 定义受限、跨平台一致的版本格式：正式 `MAJOR.MINOR.PATCH`；内测 `MAJOR.MINOR.PATCH-beta.N`，`N` 为无前导零的正整数。前三段各为 0–65,534 的整数以兼容 Windows 程序集版本；`N` 最大为 2,147,483,647。各数字无前导零，版本总长度最多 128 字符；拒绝 alpha、rc、构建元数据、无效或溢出版本。示例：`1.7.0-beta.2 < 1.7.0-beta.11 < 1.7.0 < 1.8.0-beta.1`。OS 版本解析继续独立于产品版本。
- 开关关闭时仅从 `stable[本平台]` 选择比已安装版本更高、满足最低系统版本的条目；开启时同时考虑 `stable` 和 `beta`，选择两者中满足条件且版本最高的一个。无合格候选时不显示升级。每个平台单独比较，不能使用另一平台的包或证明。
- 完整产品版本包括 `-beta.N`，贯穿 UI、更新事件 ID、跳过/稍后、清单、Release/tag、包名、provenance、安装任务和包校验，不能只取数字主版本。正式版与相同数字的 Beta 仍是不同版本。
- macOS 的系统 bundle 版本使用合法的 `MAJOR.MINOR.PATCH`，完整版本另保存在签名覆盖的应用元数据中，并与安装包 provenance、发布 tag 一致；仅能在 provenance 表明是旧正式发布、其数字版本与 bundle 版本一致且无 Beta 身份时，才允许回退数字版本。完整字段缺失但来源不明、显示 Beta 或字段与 provenance/tag 不一致时更新检查应报身份错误，不可把 Beta 降格当作同数字正式版。Windows 用经过构建和包校验的应用元数据保留完整版本，程序集数字版本仍满足系统要求；不能从 `Assembly.GetName().Version` 推断 Beta 序号。用户界面和更新器都必须读取完整身份，开发候选需继续明确标识，不能冒充已发布包。
- 任一跨层版本、渠道、平台、来源提交或摘要不一致都拒绝安装。下载时从 GitHub 精确 tag 重新解析 Release 和资产；正式条目仅接受 `prerelease=false`，内测条目仅在用户当前允许内测时接受 `prerelease=true` 且 tag 精确匹配 Beta 格式。绝不把“允许 Beta”当作放宽 URL、摘要、来源或平台校验的开关。

## 更新清单与兼容性

继续使用同一个 `updates.json` 与 `schemaVersion: 1`，保留现有 `stable` 原结构和地址，新增可缺省的 `beta` 对象，字段结构与 `stable` 一致，每个对象独立按 `macos-arm64`、`windows-x64` 存放最高合格版本。旧客户端忽略新增字段，只读取 `stable`；新客户端可读取旧清单，缺少 `beta` 表示暂无内测包，不影响正式更新。示意如下（仅示意结构，实际链接必须符合既有允许列表）：

```json
{
  "schemaVersion": 1,
  "stable": { "macos-arm64": { "version": "1.7.0" } },
  "beta": { "macos-arm64": { "version": "1.8.0-beta.1" } }
}
```

示例省略现有必填的 `minOS` 和 `releaseNotesURL` 等字段，不能直接作为可部署清单。客户端分别验证渠道及本平台条目，不能把预发布误读为正式条目；关闭内测时忽略 Beta 字段，开启时若 Beta 字段畸形则不推荐 Beta、明确表示内测检查失败，但仍应允许已验证的正式条目正常工作。无 Beta 条目与 Beta 畸形需区分；正式清单本身无效时整个检查失败，不能绕过它仅依赖 Beta。检查返回过期缓存或网络失败时不回退到未经验证的包；沿用现有限流和重试。

生成器从 GitHub 公开 Releases 分页读取，跳过草稿、未发布、渠道与 tag 不一致及资产不完整的条目。正式字段只采纳正式发布，Beta 字段只采纳匹配 Beta tag 的 GitHub 预发布；两类都执行现有平台资产、完整性、provenance 和原生验证证明门禁。按平台独立选择最高合格版本，Beta 缺某平台时不影响正式字段。证明读取或校验出现不确定的网络/完整性错误时，部署应失败并保留已部署清单，不能用部分错误结果覆盖；显式缺少某个新版本平台资产则可继续选择该平台较旧的合格版本。

## 通道切换与并发

渠道选择作为更新检查与安装任务的授权状态，不只是展示过滤：

- 每次开启或关闭成功后递增本机渠道代次；在途请求、缓存复用、通知投递和安装按钮动作都检查当前代次和资格。旧请求返回、HTTP 304、旧提醒动作或缓存不得在关闭后重新暴露 Beta。渠道切换后可复用已验证的清单数据，但必须按当前资格重新选择。
- 开始 Beta 下载及交接前再次检查资格和目标版本；关闭和交接竞争必须在同一串行状态机内决定先后。关闭先成功则取消并等待可取消任务退出、拒绝后续交接；交接先进入不可取消阶段则暂时不允许关闭，避免界面声称关闭后仍开始安装。
- 禁止旧 Beta 提醒触发安装。能取消的待发提醒取消；已发给系统或外部通知服务的内容不保证能撤回，点击时仍需重新验证当前资格。更新历史可保留，但不能因历史消息绕过当前渠道检查。
- 更新检查和安装验证均独立做渠道校验，不能仅相信服务器字段、屏幕上的按钮状态或先前一次确认。

## GitHub 发布与运维

1. Release Please 在专用 Beta 分支生成和维护预发布版本、版本文件及带 `-beta.N` 的 tag；正式分支仍按现有正式 Release Please 流程。合并/发布由维护者分别操作；先在不发布到生产的隔离 CI 中验证 Beta 序号及回归至正式分支的版本生成。
2. GitHub 内测 Release 显式标记为 **pre-release**，不可标为 latest；正式 Release 不标记 prerelease。tag 和安装包文件名保留完整 Beta 后缀，macOS DMG、Windows ZIP 各自独立带平台标识及现有校验资产，不覆盖已有资产。
3. 修改 staged 打包/校验允许严格限定的 Beta tag，并保证版本文件、精确 tag、源码提交、两种版本身份及平台证明一致；不得通过跳过验证、复用正式资产或修改已发布包来完成 Beta。macOS 继续原生启动与签名校验，Windows 继续原生启动/安装升级回滚卸载证明；平台可分阶段发布，清单只纳入证据完整的平台。
4. 在预发布平台发布成功后，现有 Pages 工作流使用默认分支受控生成器重新生成并原子部署同一清单；失败保留上一份。正式渠道的选择不因 Beta 发布而变化。首次 Beta 发版前须先交付支持 Beta 的正式客户端、其随包更新助手和清单生成器：升级事务使用当前已安装版本的助手，因此不能只在待安装 Beta 包中加入兼容逻辑。旧客户端无论是否打开旧版设置都继续只识别正式版。
5. 在真正创建或公开任何 Beta 或正式 Release 前，仍需用户对具体发布的明确授权；仅设计、候选打包、测试或推送不等于发布授权。

## 验收与验证

- **交互**：双平台新安装及旧偏好迁移默认关闭；每一步取消、关闭窗口、键盘和读屏操作；重复尝试、重启、保存失败和切换持久性；内测偏好损坏仅使内测关闭，其他原有设置及文件不被重置或覆盖；深浅色、高对比、三语言、窄窗口；已选 B 卡片与状态文案。
- **版本/清单**：共享跨语言样例覆盖正式与 Beta 顺序、同主版本从 Beta 到正式、两平台错位、无 Beta、旧 schema 1 清单、Beta 畸形但正式可用、非法版本、溢出、伪造 URL、错误平台/系统版本、草稿和 Release 标记不匹配；老客户端仍忽略 Beta 字段。
- **链路安全**：分别对 Release/tag/包名/摘要/来源/平台/完整版本/系统 bundle 数字版本/provenance 的篡改做拒绝测试，覆盖 Beta 完整身份缺失和旧正式包回退；Beta 资格关闭时下载和安装均拒绝；保留现有下载限制、签名、回滚和数据保存测试。以实际随包助手端到端验证“支持 Beta 的正式版 → beta.1 → beta.2 → 相同数字的正式版”。
- **竞态**：自动检查在切换前后返回、304 缓存、旧提醒点击、重复手动检查、关闭时下载/校验取消、关闭与安装交接同时发生、失败恢复与应用重启；确认不会错误开启或自动降级。
- **发布**：用隔离的模拟 Release/tag 与资产验证双渠道生成器和 staged 工作流，检查无覆盖、标签/元数据一致以及平台部分缺失；macOS 与 Windows 各自运行原生构建、安装、升级和回滚测试，再分别记录实际设备验收。跨编译、截图或另一平台通过不能代替 Windows 原生执行。
