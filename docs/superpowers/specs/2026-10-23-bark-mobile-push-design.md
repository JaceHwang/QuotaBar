# QuotaBar Bark 手机推送设计

日期：2026-10-23（Asia/Shanghai）。状态：用户已确认规格，并授权生成计划后直接多智能体并行实施。
代码基线：`ef80385`；已安装持续气泡版产品源码为`c648ce3`。范围为macOS/Windows及简中、繁中、英文，不包含公开发布或main合并。

## 1. 已确认的需求与视觉

用户已安装Bark手机端，要求QuotaBar新增手机推送，并在设置增加独立子页供用户配置Device Key。

用户明确选择：

- 沿用现有设置的苹果原生风格直接设计，不生成效果图。保留侧栏、圆角卡片、字体、配色、浅深色、键盘与读屏支持。
- **有效提醒产生就推送，独立于气泡。** 锁屏、隐藏浮窗、暂停气泡、桌面展示方式为关闭或仅系统通知，都不阻挡手机通道。

成功标准：配置并主动启用后，已有有效恢复、Bank到期、软件更新事件可分别触达桌面与Bark；同一事件不因持续显示或普通刷新重复向手机发送；Key安全保存；网络失败不影响额度查询和桌面通知。

手机推送不新增恢复判断、低额度预警或预测，不使用MCP调用，不需要新增QuotaBar服务器或付费API。

## 2. 第一版边界

- 单个Bark设备Key，固定官方服务器`https://api.day.app`。不加入自建服务器编辑、多设备、任意请求URL或手机远程控制。
- 自动手机推送默认关闭；无Key无法开启。保存Key不自动启用，不主动发测试消息。
- 自动转发真实恢复、Bank、软件更新提醒，继续受原有各类提醒开关、确认条件、跳过/稍后策略约束。现有“庆祝开启也生成恢复提醒”的行为保留。
- 本地“预览气泡/预览庆祝”等示例不自动发手机，避免调试桌面时骚扰；手机页提供独立“发送测试推送”，明确只使用示例数据。
- Bark/iOS控制手机通知展示、声音和专注模式；不启用critical或循环铃声，不承诺把桌面“额度不变持续显示”复制到iOS。
- 桌面关闭气泡或额度变化不自动撤回已发送的手机通知；电脑退出/真正休眠不能继续产生新查询或发送。唤醒后只处理现有规则允许的新鲜事件，不补发历史。

## 3. 设置子页

在现有侧栏末尾新增第五页“手机推送”，保留现有四页顺序和更新入口索引，避免改变旧导航目的地。

页面使用现有最大内容宽度、可滚动卡片与原生控件：

1. 标题“手机推送”，说明“通过Bark接收额度恢复、Bank到期和软件更新提醒”。
2. 连接卡片：Bark标识文字、普通“启用手机推送”开关、官方服务器只读标签、Device Key密码框。
3. 操作行：“保存Key”“清除Key”“发送测试推送”。已保存时显示“已配置”；输入框不自动读回完整Key，留空不等于清除。清除是显式操作，并关闭自动推送。
4. 状态卡片：未配置/已配置/安全存储不可用/请求中/服务已接受/发送失败或结果未知；显示最近操作时间和本地化错误分类，不显示服务端原始响应。
5. 简短说明：独立于桌面气泡；启用后标题和正文会经HTTPS发送到Bark服务与APNs；Key不写日志；测试按钮仅发送示例。

测试按钮可以在自动推送关闭时验证已保存配置，不改变自动开关、恢复基线或真实收据。发送中禁用重复测试；成功只称“Bark服务已接受”，不能冒称手机已实际展示。手机号、邮箱和Apple Device Token均不需要配置。

未保存的输入保留在当前编辑控制器草稿中，页面重建不把空框误写成删除；安全写入失败时保留原凭据和开关，不显示虚假的保存成功。

## 4. 事件分流与原策略兼容

现有路由在桌面mode=off时提前返回，且“实际展示/系统接受”共享shown回执。不能直接把Bark挂在presentBubble或现有shown回调上，否则会受窗口/权限/先完成渠道影响。

调整为统一有效事件入口，再分为两个独立分支：

- 桌面分支：沿用当前bubble/system/both/off、气泡暂停、可见性、未读和持续显示规则。
- 手机分支：独立检查Bark开关、Key、事件有效性和手机去重，不读取桌面可见性/暂停/系统通知权限。

两端共享语义：同一事件分别记录桌面与Bark渠道状态；任一有效渠道首次实际展示或被服务接受，可触发原事件的一次shown回执，使Bark单独启用时软件更新也能正确记录notified。共享回执不得阻止另一通道发送；手机接受不把桌面未读标为已读。

关闭所有桌面渠道仍可只用Bark。关闭Bark不取消桌面通知；关闭原类别开关/skip/snooze、账户变化或退出时，取消对应未发送及进行中的手机任务。软件更新保持独立于账号。

异步完成绑定原事件ID、认证epoch（适用时）、投递generation和配置generation；旧请求不得更新新账号、新Key或新事件的状态。请求已经交给Bark/APNs后无法保证撤回，UI不作撤回承诺。

## 5. HTTP协议与数据最小化

官方依据：

- [Bark教程](https://github.com/Finb/Bark/blob/master/docs/tutorial.md)：`POST /push`，Key可放JSON请求体。
- [参数](https://github.com/Finb/Bark/blob/master/docs/en-us/params.md)：title、body、device_key、group、level及各自含义。
- [服务端响应](https://github.com/Finb/bark-server/blob/master/router.go)与[push实现](https://github.com/Finb/bark-server/blob/master/route_push.go)。

请求固定使用HTTPS JSON，不将Key或通知正文拼入URL，不跟随HTTP重定向，正常验证TLS证书：

```json
{
  "device_key": "<仅从系统安全凭据读取>",
  "title": "额度已恢复",
  "body": "5 小时额度剩余 100%；7 天额度剩余 36%",
  "group": "QuotaBar",
  "level": "active"
}
```

只发送已有通知标题/正文、必要Device Key和固定分组/普通优先级。不发送账号邮箱、头像、登录凭据、原始协议响应或日志。软件更新可附现有清单已验证的发布链接；恢复/Bank不伪造可打开电脑详情的手机链接。

最终编码负载设上限（建议3000字节），按编码后的字节数截断正文并保留有效Unicode，不拆为多条。响应限制大小（建议64KiB），同时校验HTTP成功和JSON `code=200`，不能仅根据HTTP200判成功。

首次请求总超时建议10秒；后台异步串行发送、队列最多32条。发送前再次检查事件有效性：恢复保留原5分钟新事件限制；Bank要求最新完整数据<=120秒且权益仍有效；更新复核版本/skip/snooze。排队超时和旧事件丢弃，不积压到唤醒后轰炸。

不自动重试网络超时、429或服务错误；超时属于“结果未知”，避免服务可能已接受时重复推送。后续新事件仍可正常发送，用户可显式测试配置。Bark失败不触发桌面失败提示或阻塞查询。

## 6. Key与本地状态

- macOS：系统Keychain通用密码条目；Windows：当前用户的Credential Manager通用凭据。原生实现封装在可注入SecretStore接口后。
- Key不进入UserDefaults/Preferences JSON、项目文件、日志、异常原文、URL、测试fixture或推送收据。不可用时不降级为明文文件。
- 非敏感偏好仅保存schema、enabled、随机配置generation及配置状态；实际是否存在Key以安全存储读取结果为准。
- 更新/清除Key后递增配置generation并取消旧请求，不自动补发当前或历史提醒；跨配置的晚到结果不污染新状态。
- 固定官方服务器，拒绝把完整URL误当Key发送；界面提示从Bark复制Device Key。输入只做必要长度/字符检查，不把任意文本作为请求目标。
- 需要时在内存临时读取Key，尽量缩短存活；不声称原生String可保证完全清零。不保存消息正文的长期发送历史。

## 7. 去重与持久化

每个语义事件/显式重新布防generation至多自动请求一次。持续气泡的1秒有效性检查、普通刷新、窗口显示变化、打开设置、切换桌面渠道均不触发重发。

手机去重与桌面received分开。发送前原子写入“已尝试”收据，避免重启或崩溃后重复；成功再标记服务接受。状态仅保存事件标识、generation、时间和结果分类，不保存Key、完整请求/响应或消息正文。容量建议256条/30天；不得在仍有效的事件上提前淘汰保护。

沿用恢复首次基线和Bank阶段持久化，不补发停用期间历史事件。软件更新同版本恢复进程后仍受手机收据约束；用户明确“稍后/重新布防”可形成新的合法generation，普通渠道变化不能伪造新事件。手机开关/Key变化不得自动扫描旧消息补发。

状态损坏时保留损坏文件并建立保守抑制基线，不立即重播当前更新或Bank事件。持久化失败抑制本次手机发送，桌面仍照常工作。不能承诺崩溃临界点的绝对送达。

## 8. 模块与两端接入

职责保持一致，名称可按现有命名约定调整：

| 模块 | 职责 |
| --- | --- |
| BarkPreferences | 默认关闭、非敏感配置与generation |
| BarkSecretStore | Keychain/Credential Manager安全读写、明确缺失/锁定/失败 |
| BarkPushClient | 固定端点、负载/响应校验、超时、禁止重定向，可注入transport |
| BarkDeliveryStore | 版本化原子收据、坏文件保留、容量/期限及抑制基线 |
| BarkNotificationController | 独立有效事件队列、配置/epoch取消、状态和一次回执 |
| BarkSettingsView | 第五设置页、编辑草稿、显式保存/清除/示例测试、三语言 |
| AppNotificationRouter | 在桌面off门控前按已启用通道分流，共享语义回执且保持独立渠道去重 |

Coordinator仅负责注入、连接和退出清理。macOS设置壳移除固定四页断言，保留更新页原索引与导航行为；Windows追加mobile页面key。测试覆盖五页应用与旧四页fixture，不弱化既有更新导航。

## 9. 验证与交付门槛

- 默认关闭、无Key禁止启用；保存不自动发送，清除取消并关闭；安全读写失败不误报，旧偏好及账号目录不变。
- 隐藏/锁屏/气泡暂停/桌面off或仅system时手机仍发送；类别开关关闭、无效Bank、旧epoch、skip/snooze阻止手机；不新增采集轮询。
- 两渠道任意先后成功、单方失败、同ID重入、重复刷新、重启收据、显式稍后再布防和旧配置回调均正确。
- 手机关闭不影响桌面，手机成功不消费桌面未读；纯手机更新成功写原notified一次。
- 标点、换行、emoji、超长/多字节正文、HTTP200业务失败、非JSON/过大响应、超时、429/5xx、跨域重定向不泄露Key。
- macOS/Windows本地化、浅深色、窄窗口、键盘和读屏；更新入口仍打开更新页，草稿不因刷新丢失。
- 单元/集成测试只使用假的Key与注入transport/SecretStore，不访问真实Bark或用户安全凭据。运行完整治理和两端原生CI，设备检查各自记录。
- 真实手机测试由用户在设置自行填Key后显式点击“发送测试推送”，只能用户确认实际送达；API成功不能替代手机证据。
- README、隐私、排错、路线图、看板同步；新增外部数据流必须如实说明，不宣称端到端加密。本版不含Bark加密消息配置。
